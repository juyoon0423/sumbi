# 배포 계획 (상의용 초안)

> 2026-11-04 작성. **아직 아무것도 만들지 않음** — 아래 "결정할 질문"을 정하면 구현 시작.
> 금액은 서울 리전 기준 대략값(1달러 ≈ 1,400원). 결정 전에 AWS 요금 계산기로 한 번 더 확인할 것.

## 한눈에 (추천)

```
[브라우저] ──https──▶ Vercel (프론트 정적 파일, 무료)
     └──wss://api.<도메인>/ws──▶ Cloudflare(무료, 프록시·TLS·DDoS)
                                   └──https──▶ EC2 t4g.small 1대 (서울)
                                                 └ Docker Compose: nginx ─▶ backend(blue|green) ─▶ redis
GitHub Actions: 테스트 → 백엔드 이미지(arm64) → GHCR → (버튼) SSM 으로 서버에 반영 → /health 확인 → 실패 시 이전 이미지로
```

- **서버 1대로 시작.** 동시접속 상한(대기 화면)이 "몰려도 죽지 않게"를 맡고, 서버가 아예 안 되면 프론트는 이미 **혼자 하는 바다**로 넘어감.
- **배포 때 끊김은 짧게(1~3초) + 자동 재접속.** 새 컨테이너를 먼저 띄워 건강 확인 → nginx 를 넘긴 뒤 옛 서버가 "곧 다시 연결해요"(close 1012)로 닫음. 메모리 상태(방·자리·대야)는 이때 초기화 — 2단계에서 Redis 로 옮겨 이어지게.
- 평소 예상 비용 **월 약 2.9만 원**(t4g.small). 예산 1~2만 원을 꼭 지키려면 t4g.micro(약 1.8만 원)로 시작 — 질문 1.

## 1. 현재 상태 점검

### 1.1 배포하려면 바뀌어야 하는 것

| 구분 | 지금 | 배포 때 | 비고 |
|---|---|---|---|
| 실행 | `dev.sh` (gradle bootRun + vite) | 백엔드 Docker 이미지, `deploy/docker-compose.yml`(nginx·backend·redis), 프론트는 Vercel 빌드 | PLAN 9장의 `deploy/` 폴더 |
| 백엔드 이미지 | 없음 | `eclipse-temurin:21-jre` 기반, jar 만 복사(빌드는 Actions 에서), root 아님, `-XX:MaxRAMPercentage` 로 힙 제한 | arm64(t4g) 용. jar 는 CPU 종류와 무관해서 이미지 빌드가 빠름 |
| 설정 분리 | `application.yml` 기본값이 localhost | 운영 값은 **환경변수**로만 (`SUMBI_ALLOWED_ORIGINS`, `SUMBI_REDIS_URL`, `SUMBI_MAX_TOTAL` …). 서버의 `.env`(커밋 안 함) 또는 SSM Parameter Store | 이미 `${SUMBI_*:기본값}` 구조라 코드 변경은 거의 없음 |
| 허용 origin | `http://localhost:*`, `127.0.0.1:*` (+ dev.sh 가 내부 IP) | `https://<도메인>` 만 (+ 필요하면 `https://www.<도메인>`) | Vercel 미리보기 주소 허용 여부는 질문 9 |

| 프록시 | 없음 | nginx: `/ws` 업그레이드 헤더, `proxy_read_timeout` 90초 이상(하트비트 30초), `/health` | |
| 실제 IP | 연결 주소 = 브라우저 | Cloudflare·nginx 를 거치므로 `CF-Connecting-IP` → nginx `real_ip` → 백엔드 `X-Forwarded-For` | IP 당 연결 수 제한·로그용 |

| 번들 | 1.4MB 한 덩어리 (경고) | 출시를 막진 않음. 나중에 코드 분할 | |

### 1.2 서버 메모리에 있는 상태 → 배포·확장에 주는 제약

| 상태 | 어디 | 서버를 다시 켜면 | 서버 2대면 |
|---|---|---|---|
| 방·플레이어·위치·id | `Room.players` | 모두 새로 입장(새 번호, 새 방 배정) | 같은 바다가 두 서버로 나뉨 |
| 재접속 예약(20초 유예) | `GameServer.reservations` | 사라짐 → 끊긴 사람은 "새 사람"으로 들어옴 | 다른 서버로 붙으면 예약을 못 찾음 |
| 불턱 자리·걷는 중 | `Room` | 모두 바다로(또는 새 자리) | 방 주인 서버가 하나여야 함 |
| 공동 대야(차오름·회차) | `Basin` | 0 으로 | 〃 |
| 손질 장부(딴 것 → 손질 가능 수) | `PrepLedger` | 0 → **망사리는 브라우저에 남는데 손질은 못 함** (알려진 문제) | 〃 |
| 대기열 순번 | `AdmissionService` | 대기자도 다시 줄 섬 | 전체 상한을 서버끼리 나눠야 함 |
| 오늘의 바다 | Redis | **유지** | 이미 공유 |
| 망사리·꾸미기·일지 | 브라우저 localStorage | 유지 | 상관없음 |

정리하면:
- **재시작 = 모두 짧게 끊겼다 새로 들어옴.** 게임 진행이 "쌓이는" 게 거의 없어서(망사리·일지는 브라우저) 손해는 작음. 아쉬운 건 손질 장부·대야·불턱 자리.
- **WebSocket 연결은 원래 한 서버에 붙어 있음** → 연결 자체를 옮기는 방법은 없음. 무중단의 핵심은 "끊기지 않게"가 아니라 **"끊겨도 금방, 같은 상태로 다시 붙게"**.
- **두 대 이상**은 "아무 서버에나 나눠 보내기(라운드 로빈)"가 안 됨. 방 단위로 서버를 정해야 함 (3.2).

- **B(관리형 Redis)를 지금 안 하는 이유**: Redis 는 오늘의 바다 집계만 하고, 죽어도 메모리로 넘어가게 만들어 둠. 관리형으로 빼면 비용이 두 배 가까이 되는데 얻는 게 적음. 상태를 Redis 로 옮기는 2단계(3.1)나 서버 2대(3.2) 때 다시 검토.
- **참고로 흥미로운 선택지**: Cloudflare Durable Objects 는 "방 하나 = 객체 하나 + WebSocket"이라 숨비 구조와 꼭 맞지만, 백엔드를 TypeScript 로 다시 써야 해서 이번엔 제외.

## 3. WebSocket 서비스라서 고민할 점

### 3.1 새 버전 배포 때 연결이 끊기는 문제

선택지:

| | 방식 | 사용자가 겪는 것 | 할 일 |
|---|---|---|---|
| ① 그냥 재시작 | `docker compose up -d` 로 바꿔 끼움 | 5~15초 끊김(JVM 뜨는 시간) → "다시 연결하는 중" → 새 사람으로 입장 | 거의 없음 |
| ② **블루그린 + 1012 재접속** (추천, 1단계) | 새 컨테이너(green)를 옆에 띄움 → `/health` 확인 → nginx upstream 을 green 으로 바꾸고 reload → blue 가 모두에게 close 1012 → 클라이언트가 0~3초 무작위 뒤 green 에 재접속 → blue 정리 | **1~3초** "바다를 새로 단장하고 있어요" → 새 사람으로 입장 (불턱 자리·대야·손질 장부 초기화) | 종료 처리, 클라이언트 1012 처리, 배포 스크립트 |
| ③ 블루그린 + 상태 이어 받기 (2단계) | ②에 더해 재접속 예약·손질 장부·대야·불턱 자리를 Redis 에 저장 | 1~3초 뒤 **같은 번호·같은 자리**로 돌아옴 | Redis 저장 구조, 방 복원 |

- **WebSocket 연결 자체를 blue → green 으로 넘기는 방법은 없음.** nginx reload 는 기존 연결을 옛 워커가 붙잡고 있게 할 뿐이라, 결국 옛 컨테이너를 닫을 때 끊김. 그래서 "끊을 때를 서버가 정하고, 클라이언트가 바로 다시 붙게" 하는 게 핵심.
- 숨비는 쌓이는 진행이 거의 없는 힐링 게임이라 **②로 충분**하다고 판단. 다만 배포마다 모두가 1~3초 끊기므로 **배포는 자동이 아니라 버튼(또는 태그)으로, 한가한 시간에** (질문 7).
- ③은 "메모리 상태를 Redis 로 빼서 무중단 배포 + 수평 확장 준비"라는 포트폴리오 이야기가 됨. 서버 2대로 가기 전 단계로 좋음.

### 3.2 서버를 2대 이상으로 늘려야 할 때

- **문제**: 같은 바다(방)의 사람이 서로 다른 서버에 붙으면 서로 안 보임. 불턱 자리·대야처럼 "한 곳에서 정해야 하는 것"도 갈라짐.
- **해결책 두 가지**
  - **방 단위로 서버 나누기(추천)**: 방마다 주인 서버를 정함(Redis 에 `방 → 서버`, 서버별 인원). 입장할 때 빈자리가 있는 방의 서버로 보냄. nginx 가 `?room=` 으로 해당 서버에 연결하거나, 서버별 주소(`s1.api…`)로 보냄. **한 방의 위치·자리·대야는 계속 한 서버 메모리** → 지금 코드를 거의 그대로 씀.
  - **Redis Pub/Sub 로 모든 서버가 같은 방을 공유**: 위치 스냅샷(초당 10회 × 방 수)을 Redis 로 돌리고, 자리·대야 같은 결정은 분산 잠금이 필요. 구현·디버깅이 훨씬 복잡하고 지연이 늘어남. 숨비 규모엔 과함.
  - 공통으로 Redis 로 가야 하는 것: 전체 인원 상한·대기열, 재접속 예약(다른 서버로 붙어도 찾게), 오늘의 바다(이미 Redis).
- **언제 늘리나**: 부하 테스트(k6)로 잰 "1대 한계"의 70% 를 평소 최대 동시접속이 넘을 때. 그 전에는 **위로 키우기**(t4g.small → medium → large, 정지 → 타입 변경 → 시작 2~3분, 같은 IP)가 훨씬 쌈. 포트폴리오로는 "방 단위 분할 설계를 문서로 + 2대 구성 실험"까지만 해도 충분히 설명 가능.

### 3.3 사람이 갑자기 몰릴 때

- **이미 있는 안전장치**: 전체 상한 초과 시 **대기 화면**(순번 안내), 방 50명, 연결당 초당 30개·1KB 제한, 느린 연결 정리, 서버가 없으면 혼자 하는 바다.
- **더할 것**: nginx IP 당 동시 연결 수 제한(예: 10), Cloudflare 프록시(DDoS·봇 차단, 서버 IP 숨김), 재접속 무작위 지연, 상한은 **부하 테스트 후** 정함.
- **1대가 버틸 인원(추정, k6 로 확인 필요)**
  - 보내는 양: 스냅샷은 움직인 사람만 담아 약 `30 + 33 × 움직인 사람 수` 바이트, 초당 10번. 50명 꽉 찬 방에서 20명이 움직이면 한 사람이 받는 양 ≈ 초당 7KB.
  - 500명(꽉 찬 방 10개) ≈ 초당 3.5MB(28Mbps), 서버가 보내는 메시지 초당 5,000개 + 받는 메시지 5,000개. 2 vCPU 면 CPU·네트워크 모두 여유가 있을 것으로 봄 → **t4g.small 로 500~1,000명** 정도로 추정. t4g.micro(1GB)는 메모리가 빠듯해 **200~300명** 정도로 보고 스왑을 둠.
  - 주의: t4g 는 "평소엔 기본 성능, 가끔 높게" 방식. 기본 성능을 오래 넘으면 추가 과금(무제한 모드) — CloudWatch 로 CPU 크레딧을 봄.
- **처음 상한 추천**: 전체 300명, 방 50명 → k6 로 한계를 재고 그 70% 로 조정 (progress "다음 할 일" 3번).
- **서버 사양 추천**: **t4g.small(2 vCPU, 2GB)**, 힙 768MB, Redis 64MB 제한, 디스크 20GB gp3.

## 4. 그 밖에 정할 것

### 4.1 도메인과 HTTPS
- 구조: `https://<도메인>`(+ `www`) → Vercel / `wss://api.<도메인>/ws` → 서버.
- **DNS 는 Cloudflare(무료)** 에 둠 (도메인은 어디서 사도 됨. `.kr` 은 가비아 등, `.com/.app` 은 Cloudflare 에서도).
  - 프론트 레코드: Vercel 안내대로(Cloudflare 프록시 끄기 = 회색 구름).
  - `api` 레코드: **프록시 켜기(주황 구름)** → 브라우저에는 Cloudflare 인증서, 서버(nginx)에는 **Cloudflare Origin 인증서**(15년, 갱신 걱정 없음). Cloudflare 무료도 WebSocket 지원, 유휴 100초 제한은 하트비트 30초라 문제없음.
  - 대안: Cloudflare 없이 nginx + Let's Encrypt(certbot 자동 갱신, 80 포트 열기). 해 봤던 방식이지만 서버 IP 가 드러나고 DDoS 보호가 없음.

### 4.2 CI/CD
- **이미지 빌드**: GitHub Actions. jar 빌드(테스트 포함) → `docker buildx` 로 arm64 이미지 → **GHCR**(`ghcr.io/<계정>/sumbi-backend:<커밋>`). 로컬 Mac 빌드는 사람마다 결과가 달라질 수 있고, Docker Hub 는 따로 계정·토큰이 필요해서 GHCR(저장소 권한 그대로) 추천.
- **프론트**: Vercel 의 GitHub 연결로 main push 때 자동 배포 (Actions 에선 lint·빌드만 검사).
- **서버 반영**: Actions → **AWS SSM Run Command** (GitHub OIDC 로 AWS 역할을 받아서, 키를 저장하지 않음). 서버의 `deploy.sh <태그>` 가 이미지 받기 → green 띄우기 → `/health` 확인 → nginx 전환 → blue 에 종료 신호 → 정리.
  - SSH 방식(Secrets 에 키, 22 포트 열기)은 해 봤던 방식이지만 22 포트를 GitHub 전체 IP 대역에 열어야 해서 비추천.
- **흐름**: PR·push → 테스트·lint·빌드(자동) / main → 이미지 푸시(자동) / 서버 반영은 **수동 버튼**(`workflow_dispatch`, 태그 입력) — 배포마다 모두 1~3초 끊기므로.

### 4.3 되돌리기
- 이미지는 커밋 해시로 태그, 서버엔 최근 5개 보관. `deploy.sh` 가 새 버전 `/health` 실패 시 **자동으로 이전 태그 유지**(전환 안 함).
- 수동 되돌리기: Actions 의 배포 버튼에 이전 태그 입력(= 같은 절차). 서버에 들어가 `deploy.sh <이전 태그>` 도 가능.
- Redis 데이터는 오늘의 바다뿐이라 되돌릴 일 없음. 2단계에서 상태를 Redis 로 옮기면 키 이름에 버전(`sumbi:v1:…`)을 붙여 옛 버전과 섞이지 않게.

### 4.4 서버 보안
- 보안 그룹: **443 만** 공개(Cloudflare IP 대역만 허용하면 더 좋음). 22 포트는 닫고 **SSM Session Manager** 로 접속. 80 은 Let's Encrypt 를 쓸 때만.
- 컨테이너: 백엔드 8080·Redis 6379 는 외부로 안 엶(Compose 내부 네트워크), 백엔드는 root 아닌 사용자, Redis 는 보호 모드 + 메모리 제한.
- OS: 자동 보안 업데이트, Docker 로그 크기 제한(10MB × 3).
- 비밀: 서버 `.env` 는 SSM Parameter Store 에서 받아 생성(저장소에 없음). 지금 백엔드엔 진짜 비밀이 거의 없음(Redis 비밀번호 정도).
- AWS 계정: 루트 MFA, 관리용 IAM 사용자, **예산 알림**(1만·2만·3만 원).
- 앱: origin 은 운영 도메인만, 기존 속도 제한·메시지 크기 제한 유지.

### 4.5 로그와 모니터링 (최소 비용)
- 1단계(무료):
  - **업타임 감시**: UptimeRobot 또는 Better Stack 무료로 `https://api.<도메인>/health` 5분마다 + 메일 알림.
  - **CloudWatch 기본 지표**(CPU·네트워크·CPU 크레딧) + 알람 2~3개(무료 10개 안).
  - **로그**: `docker compose logs`, 파일 회전. 백엔드는 1분마다 한 줄 요약(방·인원·대기·메시지 수·끊긴 연결 수).
- 2단계(포트폴리오용, 무료 한도): Spring Actuator + Micrometer → Grafana Cloud 무료(대시보드: 동시접속·방 수·초당 메시지·전송 줄 길이·GC).
- CloudWatch Logs 로 보내는 건 수집·보관 요금이 붙어서 1단계에선 안 함.

## 5. 로컬 Docker

| | dev.sh 만 | dev.sh + 로컬 compose 확인 (추천) | 로컬도 늘 compose |
|---|---|---|---|
| 평소 개발 속도 | 빠름(HMR, bootRun) | 빠름 | 느림(이미지 다시 빌드) |
| 운영과 같은지 | nginx·TLS 없는 구성만 확인 | 배포 전에 **nginx 업그레이드 프록시·이미지·헬스 체크·종료 처리**를 Mac 에서 확인 | 늘 같음 |
| Docker Desktop | 필요 없음 | 확인할 때만 켬 | 늘 켜야 함(메모리) |

- 추천: **평소엔 dev.sh 그대로**, `deploy/docker-compose.yml` 을 로컬에서도 띄울 수 있게(`docker-compose.local.yml` 로 TLS 대신 http, 이미지는 로컬 빌드) 해 두고, **Dockerfile·nginx·종료 처리를 바꿀 때와 첫 배포 전**에만 켬. 이때 `capture-multiplayer.mjs` 를 nginx 경유 주소로 돌려 연결·재접속을 확인.
- Actions 가 같은 이미지를 빌드하므로 로컬 Docker 는 "미리 확인용"이고 필수는 아님.

## 6. 추천 구성 (한 줄씩)

1. **EC2 t4g.small 1대(서울) + Docker Compose(nginx·backend·redis)** — 해 본 구성이라 빠르고, 비용 대비 여유가 크고, 왜 이렇게 했는지 모두 설명 가능.
2. **Cloudflare 프록시 + Origin 인증서** — TLS 갱신 걱정 없음, DDoS·봇 차단, 서버 IP 숨김, 무료.
3. **블루그린 + close 1012 + 무작위 재접속** — WebSocket 은 연결을 넘길 수 없다는 걸 인정하고 끊김을 1~3초로 줄이는 설계. 2단계에서 상태를 Redis 로 옮겨 "같은 자리로 복귀".
4. **GitHub Actions → GHCR → SSM(OIDC)** — 키·SSH 포트 없이 배포, 커밋 태그로 되돌리기.
5. **동시접속 상한 + 대기 화면 + 혼자 하는 바다** — 몰려도 서버가 아니라 줄이 길어지고, 서버가 죽어도 화면은 살아 있음. 상한은 k6 로 정함.
6. **확장은 위로 먼저, 옆으로는 방 단위 분할** — 지금 코드 구조(방 = 한 서버)를 그대로 살림.

포트폴리오로 설명할 이야기: "실시간 WebSocket 서비스의 무중단 배포 문제 → 연결은 못 옮기니 끊김을 짧게 + 상태를 외부로 → 방 단위 수평 확장 설계", "몰림 대비를 서버 증설이 아니라 입장 제어·우아한 저하(혼자 하는 바다)로", "비용 2~3만 원 안에서".
